# Shared Windows Build-Tools Preflight Contract

> Status: Qualification contract
> Platform: Windows
> Scope: Shared technical prerequisites for the desktop build-chain qualification candidates.

## Purpose

Provide a reproducible, minimally invasive Windows environment for comparing the desktop build-chain candidates.

The shared environment must be established before candidate-specific implementation begins.

## Frozen shared versions

The qualification uses exactly:

- Node.js: `24.14.0`
- pnpm: `11.4.0`
- Electron Forge: `7.11.2`
- Electron: `43.2.0`

`latest` is not permitted for these shared qualification versions.

Both candidates must use the same frozen versions.

## Runtime requirements

- BT-01: Platform is Windows.
- BT-02: Node.js resolves to exactly `v24.14.0`.
- BT-03: Repository `packageManager` selects pnpm `11.4.0`.
- BT-04: Corepack is executable.
- BT-05: `ComSpec` is available.
- BT-06: `PATHEXT` includes `.CMD`.
- BT-07: pnpm is executable through the Windows command path used by child processes.
- BT-08: Resolved pnpm version is exactly `11.4.0`.

## Shared frozen-version input verification

The previous BT-44 and BT-45 wording required candidate-installed dependency
resolution before candidate bootstrap. That interpretation is superseded because
it conflicts with BT-35, which requires both candidate directories to remain in
the approved empty placeholder state before qualification begins.

For Shared Preflight, BT-44 and BT-45 verify frozen candidate inputs. Actual
installed dependency resolution is verified later by each candidate's
qualification and acceptance evidence.

- BT-44 (Current): Candidate A and Candidate B must both use Electron Forge
  `7.11.2` as the shared frozen qualification input.
- BT-45 (Current): Candidate A and Candidate B must both use Electron `43.2.0`
  as the shared frozen qualification input.

Superseded interpretation:

- BT-44 (Superseded): Both candidates must already resolve Electron Forge
  `7.11.2` before candidate bootstrap.
- BT-45 (Superseded): Both candidates must already resolve Electron `43.2.0`
  before candidate bootstrap.

## Temporary launcher requirements

- BT-09: Corepack pnpm shims must be created only in an approved writable temporary directory.
- BT-10: Temporary shim paths must be process-scoped and must not be persisted to User or Machine `PATH`.
- BT-11: The launcher must not modify PowerShell ExecutionPolicy.
- BT-12: The launcher must not require administrator privileges.
- BT-13: Temporary launcher artifacts must be removable after execution.

## pnpm security requirements

- BT-14: Bootstrap-only pnpm security exceptions must be process-scoped and reversible.
- BT-15: `blockExoticSubdeps` must not be persistently disabled through global pnpm configuration.
- BT-16: Temporary pnpm security exceptions must not remain after the launcher exits.

## Git dependency transport

- BT-17: Public Git dependencies required by the build toolchain must support HTTPS transport.
- BT-18: Public Git dependency fetches must support non-interactive execution.
- BT-19: Required pinned Git commits must be fetchable and verified by resulting object identity.
- BT-20: Public dependency installation must not require a private SSH identity.
- BT-21: Temporary Git environment variables must be removed after execution.

## Long-path requirements

- BT-22: Windows long-path support must be enabled.
- BT-23: The frozen Node.js runtime must successfully create, read, and remove a file whose path exceeds 260 characters.
- BT-24: Git long-path operations must use command-scoped `-c core.longpaths=true` when required.
- BT-25: Qualification setup must not require modification of global Git `core.longpaths`.
- BT-26: Long-path checks must verify the intended Git effect, not only the process exit code.

## Temporary storage requirements

- BT-27: The temporary directory must support create, write, read, and delete operations.
- BT-28: The pnpm store path must resolve successfully.
- BT-29: Qualification probes must clean up disposable temporary artifacts.

## Network requirements

- BT-30: npm Registry HTTPS access must succeed.
- BT-31: GitHub HTTPS access required by public build dependencies must succeed.
- BT-32: Electron release assets must be reachable through their redirect and asset-delivery chain.

## Candidate isolation and fairness

- BT-33: Both candidate worktrees must begin from the same Git commit.
- BT-34: Both candidate worktrees must be clean before qualification begins.
- BT-35: Each candidate directory must begin from the approved empty placeholder state.
- BT-36: Candidate A and Candidate B must use separate cold pnpm stores.
- BT-37: A candidate may reuse cache generated by its own subsequent runs, but must not consume the other candidate's qualification store.
- BT-38: Both candidates must use the same shared launcher and preflight behavior.

## Packaging scope

The shared qualification targets unsigned Windows packaging.

The verified packaging chain is based on:

- Electron Forge `7.11.2`
- `@electron-forge/maker-squirrel` `7.11.2`
- `electron-winstaller` `5.3.0`

Production code signing is outside this shared qualification contract.

## Native-module boundary

Native source compilation is not required by this desktop build-chain qualification.

If a native dependency is introduced later, a separate native-build gate must verify the required Python, compiler, Windows SDK, and Electron rebuild toolchain before that dependency is accepted.

## Fresh-shell reproducibility

- BT-39: Qualification must be able to start from a fresh PowerShell session.
- BT-40: Qualification must not depend on environment mutations left by an earlier debugging session.
- BT-41: Public dependency operations after launcher initialization must run without interactive credential prompts.
- BT-42: All temporary launcher state must be process-scoped or explicitly cleaned up.
- BT-43: A fresh-shell rehearsal must pass before this shared preflight is considered qualified.

## Verification behavior

A successful command exit code alone is not sufficient when the expected effect can be independently verified.

Where practical, checks must verify the resulting state, such as:

- the exact pnpm version actually executed;
- a long-path file actually entering the Git index;
- the requested pinned Git commit actually becoming `FETCH_HEAD`;
- temporary artifacts actually being removed.

A failed required check must report the corresponding `BT-*` identifier.

## Public repository boundary

Probe output, tests, documentation, and evidence must not expose:

- credentials, tokens, private keys, or passphrases;
- local usernames;
- private absolute paths;
- machine-specific private identifiers;
- production data or private logs;
- internal project governance, time accounting, private risk records, or confidential planning information.
